# 自动配置到底是谁实现的

> 所有数据来自本机 Maven 仓库（Spring Boot **4.1.1**），用 `javap` 反编译验证，非推测。

---

## 0. 一句话结论

**starter 什么也不实现，它只负责"把该在 classpath 上的东西放上去"。**

自动配置的实现由三个部分分工完成，其中**最后一棒根本不是 Spring Boot 干的**：

| 角色 | 是谁 | 住在哪个 jar |
|---|---|---|
| **触发** | `@EnableAutoConfiguration` → `@Import(AutoConfigurationImportSelector.class)` | `spring-boot-autoconfigure.jar` |
| **算清单（执行者）** | `AutoConfigurationImportSelector` | `spring-boot-autoconfigure.jar` |
| **读文件** | `ImportCandidates` | `spring-boot.jar` |
| **元数据（数据）** | `META-INF/spring/*.imports` | 各场景模块：`spring-boot-webmvc.jar`、`spring-boot-tomcat.jar`、`spring-boot-jdbc.jar` … |
| **具体条件注解** | `@ConditionalOnClass` / `@ConditionalOnMissingBean` … | `spring-boot-autoconfigure.jar` |
| **★ 真正注册 Bean** | `ConfigurationClassPostProcessor` | **`spring-context.jar`（Spring Framework）** |
| **★ 条件注解本体** | `@Conditional` | **`spring-context.jar`（Spring Framework）** |

> **Spring Boot 只做了"发现该配什么"，"配"这个动作一直是 Spring Framework 的老本行。**

## 1. 触发：`@EnableAutoConfiguration` 头上挂着一个 `@Import`

用 `javap -v` 看它的常量池，能看到真实注解：

```
#31 = Lorg/springframework/boot/autoconfigure/AutoConfigurationPackage;
#32 = Lorg/springframework/context/annotation/Import;
#33 = Lorg/springframework/boot/autoconfigure/AutoConfigurationImportSelector;
```

翻译成源码：

```java
@Target(TYPE) @Retention(RUNTIME) @Documented @Inherited
@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)   // ★ 全部秘密就在这一行
public @interface EnableAutoConfiguration { ... }
```

**它自己没有任何逻辑**，只是个开关，一转手把活交给 `AutoConfigurationImportSelector`。

来源链：`@SpringBootApplication`（三合一）里包含 `@EnableAutoConfiguration`。

---

## 2. 执行者：`AutoConfigurationImportSelector`

`javap` 反编译出的方法清单，等于把工作流程直接告诉了你：

```java
public class AutoConfigurationImportSelector
    implements DeferredImportSelector, BeanClassLoaderAware, ResourceLoaderAware,
               BeanFactoryAware, EnvironmentAware, Ordered {

  public String[] selectImports(AnnotationMetadata);                    // 入口：返回"该注册哪些类"的名字
  protected AutoConfigurationEntry getAutoConfigurationEntry(...);      // 算出候选清单
  protected final <T> List<T> removeDuplicates(List<T>);                // 去重
  private void checkExcludedClasses(List<String>, Set<String>);         // 处理 exclude
  protected List<AutoConfigurationImportFilter> getAutoConfigurationImportFilters();
  private void fireAutoConfigurationImportEvents(...);                  // 发事件（条件报告来源）
  ...
}
```

### 注意它实现的第一个接口：`DeferredImportSelector`

**"延迟"导入选择器** —— 这不是随便实现的，它保证自动配置**在自己的 `@ComponentScan` 扫完之后才执行**。

这正是 `@ConditionalOnMissingBean` 能生效的前提：**你的 Bean 得先注册，框架才好意思说"你有我就不管了"**。

## 3. 读文件：`ImportCandidates`

```java
public final class ImportCandidates implements Iterable<String> {
  private static final String LOCATION;                                  // ← "META-INF/spring/%s.imports"
  public static ImportCandidates load(Class<?>, ClassLoader);            // ★ 加载清单
  private static Enumeration<URL> findUrlsInClasspath(ClassLoader, String);  // ★ 扫全部 jar
  private static List<String> readCandidateConfigurations(URL);          // ★ 逐行读
  private static String stripComment(String);                            // 支持 # 注释
}
```

### 反编译出的常量池（真实值）

```
#39 = String  #40   // META-INF/spring/%s.imports
#40 = Utf8           META-INF/spring/%s.imports
#159 = String #160  // #
```

**这就解释了那个文件名为什么那么长：它是模板拼出来的。**

```
模板:   META-INF/spring/%s.imports
%s  =   @EnableAutoConfiguration 的全限定名
      =   org.springframework.boot.autoconfigure.AutoConfiguration

拼出来: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

> 记住这个模板，你以后看到任何 `.imports` 都能立刻反应出它是给哪个注解用的。

### 副产物：Boot 4 里每种注解都有自己的 `.imports`

`spring-boot-webmvc` 里实际躺着 3 份（因为用了 3 种注解）：

```
META-INF/spring/org.springframework.boot.actuate.autoconfigure.web.ManagementContextConfiguration.imports
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
META-INF/spring/org.springframework.boot.web.server.test.AutoConfigureWebServer.imports
```

### `findUrlsInClasspath` 是关键

**它不是读某一个文件，而是把 classpath 上所有 jar 里的同名文件全找出来**，合并成一份候选名单。
所以你有 10 个 starter，就是 10 份 `.imports` 被汇总，最后 `removeDuplicates` 去重。

## 4. 元数据长什么样：`spring-boot-webmvc` 的 6 行

```
[1] DispatcherServletAutoConfiguration
[2] WebMvcAutoConfiguration
[3] WebMvcObservationAutoConfiguration
[4] WebMvcHealthEndpointExtensionAutoConfiguration
[5] WebMvcMappingsAutoConfiguration
[6] ErrorMvcAutoConfiguration
```

**纯文本，只有类名，没有任何代码。** 这就是"数据"。

---

## 5. 条件注解：不是所有列出来的都会生效

`WebMvcAutoConfiguration` 的常量池里（真实存在的条件注解）：

```
Lorg/springframework/boot/autoconfigure/condition/ConditionalOnClass;
Lorg/springframework/boot/autoconfigure/condition/ConditionalOnMissingBean;
Lorg/springframework/boot/autoconfigure/condition/ConditionalOnWebApplication;
Lorg/springframework/boot/autoconfigure/condition/ConditionalOnBooleanProperty;
```

含义：

| 注解 | 检查什么 |
|---|---|
| `@ConditionalOnClass` | classpath 里**有没有**这个类 |
| `@ConditionalOnMissingBean` | 你自己**没定义过**，我才给默认的 |
| `@ConditionalOnWebApplication(type = SERVLET)` | 是不是 servlet 类型的 Web 环境 |
| `@ConditionalOnBooleanProperty` | 某个配置项是不是 true |

> **`@Conditional`（本体）住在 `spring-context.jar`，是 Spring Framework 的。**
> `@ConditionalOnClass` 这些具体实现才是 Spring Boot 加的。

---

## 6. ★ 最后一棒：真正注册 Bean 的不是 Spring Boot

`AutoConfigurationImportSelector` 自己**也不注册 Bean**。
它只负责"**算出该注册哪些类的名字**"，返回一个 `String[]`。

真正把 `@Bean` 变成容器里 Bean 的是：

```
org.springframework.context.annotation.ConfigurationClassPostProcessor
    ← 住在 spring-context-7.0.9.jar 里（Spring Framework 的）
```

它负责执行配置类里的 `@Bean` 方法、处理 `@Import`、处理扫描结果。

**所以：Boot 发现"该配什么"，Framework 执行"配"。** 这也是为什么 Spring Boot 不等于另一个容器。

## 7. 完整链路（从一行依赖到能用的 `@GetMapping`）

```
你在 pom.xml 写 <artifactId>spring-boot-starter-web</artifactId>
        │
        ├─ 直接依赖 4 个（实测）：
        │     spring-boot-starter-jackson   → 传递依赖 spring-boot-starter
        │     spring-boot-starter-tomcat    → 传递依赖 spring-boot-starter
        │     spring-boot-http-converter
        │     spring-boot-webmvc
        │
        ▼  Maven 把这一堆 jar 铺到 classpath
   spring-boot-starter.jar          4,767 B   空壳（0 个 class 文件）
   spring-boot-autoconfigure.jar  372,740 B   ← 执行者
   spring-boot-webmvc.jar         175,435 B   ← 元数据 + 配置类
   spring-boot-tomcat.jar         125,521 B   ← 元数据 + 配置类
        │
        ▼  启动时
   @SpringBootApplication
      ├─ @ComponentScan           → 扫「你自己」的包
      └─ @EnableAutoConfiguration
            └─ @Import(AutoConfigurationImportSelector.class)
                  │
                  │  ① DeferredImportSelector：等 @ComponentScan 扫完才动手
                  ▼
            ImportCandidates.load()  ← 汇总所有 jar 的
                                        META-INF/spring/*.imports
                  │  得到一个长清单（webmvc 贡献 6 个，tomcat 贡献 5 个 …）
                  ▼
            逐个做条件检查
                  @ConditionalOnClass(DispatcherServlet.class)
                  @ConditionalOnWebApplication(type = SERVLET)
                  @ConditionalOnMissingBean
                  │  条件全过
                  ▼
            交给 Spring 的 ConfigurationClassPostProcessor
                  │  执行配置类里的 @Bean 方法
                  ▼
            DispatcherServlet、HandlerMapping、ObjectMapper、Tomcat …
            全部进容器
                  │
                  ▼
            你能写 @GetMapping 了 —— 一行配置都没写
```

## 8. 两条"自动"的路，别混（和 `02-自动包扫描.md` 配套看）

|  | 自动包扫描 | 自动配置 |
|---|---|---|
| 触发注解 | `@ComponentScan` | `@EnableAutoConfiguration` |
| 两者都在 | `@SpringBootApplication` 内部 | 同一个注解里 |
| 目标 | **你自己写的**类 | **框架/第三方**写好的配置类 |
| 发现方式 | 按**包路径**扫 `.class` 文件 | 按**清单文件**读类名 |
| 范围 | 主程序所在包及子包 | 整个 classpath 上所有 jar |
| 典型产物 | 你的 `@Service`、`@Controller` | `DispatcherServlet`、`ObjectMapper` |
| 执行者 | Spring Framework 的扫描器 | `AutoConfigurationImportSelector` |

**为什么必须要有 `.imports` 这套机制？**
因为 `@ComponentScan` 只扫你自己的包，**永远扫不到框架 jar 里的类**。
想要"隔着 jar"把自己的组件送进容器，就必须有一份主动声明的清单。

---

## 9. 实用附录：怎么看"谁生效了、谁没生效"

| 方法 | 作用 |
|---|---|
| `logging.level.org.springframework.boot.autoconfigure=DEBUG` | 看哪些自动配置类被处理 |
| 启动加 `--debug` | 启动时打印**条件评估报告**，明确列出哪些生效、哪些被哪个条件否决 |
| `@EnableAutoConfiguration(exclude = XxxAutoConfiguration.class)` | 手动关掉某个自动配置 |
| `spring.autoconfigure.exclude=...` | 用配置关掉 |

> `--debug` 打出来的那份报告，就是 `fireAutoConfigurationImportEvents` 里
> `ConditionEvaluationReportAutoConfigurationImportListener` 收集的。
