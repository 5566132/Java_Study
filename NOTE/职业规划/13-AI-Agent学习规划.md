## 〇、先回答三个关键疑问（别带错前提上路）

### 疑问1：后端和 agent 岗位解决的问题不一样，是不是冲突？

**不冲突，而且是高度重叠。** 证据：云从科技「AI Agent 平台研发」JD（20-50K）明确列出两个方向：

- **方向一：Runtime（分布式后端 / 状态持久化 / 长任务可靠性）** ← 这就是后端
- 方向二：编排·知识（多模型编排 / 上下文工程 / RAG / Prompt 工程化 / evals）

同一个 JD 强调"**不止于 Demo**"，要求讲清**重试、幂等、状态一致性、可观测性**。

**本质原因**：agent 跑起来后真正的难题不是"怎么调模型"（那是模型厂商的活），而是：
- 任务执行到一半崩了怎么恢复？（状态持久化 / 检查点）← 你学 Redis 时接触过
- 同一个工具被重复调用怎么防重？（幂等）← 秒杀项目里就有
- 并发上来怎么限流、怎么控成本？（令牌桶 / 分层模型）← 秒杀项目里就有
- 用户长对话上下文存哪、怎么压缩？（缓存策略）← Redis 那一套

**结论：后端能力是 agent 工程化的地基，不是竞争关系。**

### 疑问2：纯后端岗还有吗？

**有，但被改写成「Java 后端 + AI 集成能力」。** 真实校招 JD（河南智友云，2027 届，6-8K）的分档很说明问题：

| 硬性要求 | AI 部分 |
|---|---|
| Java / JVM / SpringBoot / **MySQL / Redis / RocketMQ-Kafka** | RAG / Agent / Prompt / Function Calling **「了解即可，有项目优先」**；Spring AI / LangChain4j **加分** |

**规律**：
- **校招**：AI 多为「了解 + 有项目优先」，后端技术栈仍是硬性
- **社招**：AI 集成能力已变成硬性（如德安石油「高级 Java（AI 应用方向）」把 Spring AI/LangChain4j 写进要求）

**市场数据**（2026 年 1-7 月）：新发 AI 岗位同比 **+789%**，AI 应用开发占 AI 招聘 **61%**，Agent 开发需求 **+244%**。同时大厂在压缩传统后端岗。→ **趋势是真的，但入口仍然是后端基本功。**

### 疑问3：那我该转方向吗？

**不要转。** 理由：
1. 你后端已投入大量时间，沉没成本之外更重要的是——**后端是 agent 工程的地基**，转掉等于自断优势
2. 算法岗（论文 / 硕博 / 顶会）和应用开发岗**不是一条赛道**，双非本科冲算法岗不现实，冲**应用开发岗**现实
3. 正确姿势：**后端主线不动，在每个项目里塞一个 agent 模块** → 简历是「Java 后端 + AI 落地」，而不是"半吊子算法"

## 二、四层学习路线（含时间、资源、产出）

> 每层标注：**⏱ 时长** ｜ **📚 跟谁学** ｜ **🎯 产出** ｜ **📅 建议时间**

### 第 1 层 · 认知层（⏱ 6-8h ｜ 📅 **就现在，穿插在 SpringBoot 之前**）

**目标**：知道 agent 是什么、能跟人聊明白、破除神秘感。**不写代码**。

> ⚠️ **这一层不是"学技术"，是"消除焦虑"。** 你现在的恐惧来自"不知道它是什么"，而不是"它很难"。花一个周末做完下面 5 步，这个词就从焦虑源变成你熟悉的领域。

#### 步骤 1 ｜ 读一篇文章（⏱ 40 分钟）

- **去哪**：https://www.anthropic.com/engineering/building-effective-agents
- **谁写的**：Anthropic（Claude 的公司）。2024 年底发布，**到 2026 年仍是这个领域被引用最多的一篇**，很多公司的 agent 设计文档直接抄它的分类。
- **看什么**：重点看它开头那个关键区分——**Workflow（工作流）vs Agent（智能体）**。它列了 5 种工作流模式（Prompt chaining / Routing / Parallelization / Orchestrator-workers / Evaluator-optimizer），然后说 agent 是"模型自己决定步骤并循环"。
- **一定要记住的一句话**（这决定你以后的设计品味）：
  > **能用 workflow 解决的，就别上 agent。** 因为 agent 不可预测、难调试、还贵。
- **看不懂怎么办**：这是英文。**用浏览器翻译插件看中文版完全够用，这篇不需要读原文。** 遇到不认识的词（tool use / context / orchestrator）先跳过，等做完步骤 4 再回来读第二遍，会豁然开朗。
- **看完的标志**：你能回答"为什么 Anthropic 建议大部分场景不要用 agent？"

#### 步骤 2 ｜ 上一门课（⏱ 2 小时）

- **去哪**：https://www.deeplearning.ai/courses/chatgpt-prompt-eng
- **课程名**：《ChatGPT Prompt Engineering for Developers》
- **谁讲的**：Andrew Ng（吴恩达）+ OpenAI 的 Isa Fulford。**免费**，B 站有搬运的带中文字幕版。
- **为什么选它**：这是 prompt 工程的**标准入门课**，1 小时 40 分钟，全程在网页沙盒里点着跑，**不用配任何环境**。
- **看什么**：重点这两节——
  - **Principle 1: Write clear and specific instructions**（怎么把话说清楚：分隔符、结构化输出、限定条件）
  - **Principle 2: Give the model time to think**（Chain of Thought：为什么"让它一步步想"效果会变好）
- ⚠️ **注意**：课程代码用的是 OpenAI 的 API，**你不用真去注册 OpenAI**（国内也不好付钱）。**看懂思路就行**，动手放到步骤 4 用 DeepSeek 做。
- **看完的标志**：你能说出"为什么给模型一个角色设定（System prompt），输出风格会不一样"。

#### 步骤 4 ｜ 用 curl 亲手调通一次（⏱ 1 小时）

**这是什么**：curl 是个命令行工具，用来发 HTTP 请求。你要做的是**跳过所有框架，直接给 DeepSeek 发一个最原始的请求**，亲眼看它返回 JSON。

**为什么必须先做**：所有框架（Spring AI / LangChain）本质上都在帮你拼这个 JSON。**你亲手拼过一次，以后框架报错你就知道它坏在哪。**

##### 4.1 确认电脑有 curl

打开 PowerShell，敲：

```powershell
curl.exe --version
```

- **有输出**（显示版本号）→ 继续
- **报错找不到** → Win10/11 自带 curl；真没有就用 4.4 的 PowerShell 版本

> ⚠️ 注意是 `curl.exe` 不是 `curl`。在 PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名，参数不一样，会踩坑。

##### 4.2 把 key 存进环境变量（只做一次）

**不要**把 key 直接写在命令里（会进命令历史）。先存成环境变量：

```powershell
# 把 sk-... 替换成你的真实 key
setx DEEPSEEK_API_KEY "sk-替换成你的真实key"
```

⚠️ 执行完**关掉 PowerShell 重新开一个**，环境变量才生效。验证：

```powershell
$env:DEEPSEEK_API_KEY
```

##### 4.3 发请求

```powershell
$body = @'
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是一个简洁的助手，回答不超过20个字。"},
    {"role": "user", "content": "用一句话解释什么是 API"}
  ],
  "stream": false
}
'@

curl.exe -s -X POST "https://api.deepseek.com/chat/completions" `
  -H "Content-Type: application/json" `
  -H "Authorization: Bearer $env:DEEPSEEK_API_KEY" `
  -d $body
```

**期望输出**（格式类似，内容不同）：

```json
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "created": 1758000000,
  "model": "deepseek-chat",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "API 是程序之间互相调用的接口约定。"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 32,
    "completion_tokens": 15,
    "total_tokens": 47
  }
}
```

**看不懂返回的字段？** 三个最重要的：
- `choices[0].message.content` ← **你要的答案在这里**
- `usage.prompt_tokens` ← 你发过去的字花了多少 token（计费）
- `usage.completion_tokens` ← 它回的字花了多少 token（计费，**更贵**）

##### 4.4 如果 curl 不好使，用 PowerShell 版

```powershell
$headers = @{
  "Content-Type"  = "application/json"
  "Authorization" = "Bearer $env:DEEPSEEK_API_KEY"
}

$body = @{
  model    = "deepseek-chat"
  messages = @(
    @{ role = "system"; content = "你是一个简洁的助手，回答不超过20个字。" }
    @{ role = "user";   content = "用一句话解释什么是 API" }
  )
  stream   = $false
} | ConvertTo-Json -Depth 5

Invoke-RestMethod -Uri "https://api.deepseek.com/chat/completions" `
  -Method Post -Headers $headers -Body $body |
  Select-Object -ExpandProperty choices |
  Select-Object -ExpandProperty message
```

##### 4.5 动手改一改（**这步最重要，别跳过**）

调通之后，**故意做这几个实验**，每个都改一下 `content` 再跑一次：

| 实验 | 改什么 | 观察什么 |
|---|---|---|
| ① System prompt 的作用 | system 改成"你是一个说话很啰嗦的老教授" | 同样的 user 问题，回答风格变了没有？ |
| ② CoT 的作用 | user 改成"一个班 30 人，60% 是女生，女生里 1/3 戴眼镜，戴眼镜的女生几人？**请一步步思考**" | 把"请一步步思考"删掉再跑，看准确率变化 |
| ③ 结构化输出 | user 里加"用 JSON 返回，字段是 name 和 age" | 它真返回 JSON 吗？稳定吗？ |
| ④ Token 计费 | 每次看返回里的 `usage` 字段 | 输入变长，`prompt_tokens` 怎么变？ |
| ⑤ **幻觉** | 问它"我昨天买的那个东西怎么样了"（它不可能知道） | 它说"不知道"，还是**给你编一个**？ |

**实验⑤的结论极其重要**：模型会一本正经地编造。**这就是为什么需要 RAG（给它真资料）和 Function Calling（让它查真数据库）**——也就是第 2、3 层要学的东西。**你亲手看它胡编一次，比读十篇文章都管用。**

##### 4.6 出错了怎么排查

| 现象 | 原因 | 解决 |
|---|---|---|
| `curl: (6) Could not resolve host` | 网络/DNS 问题 | 检查网络；公司网络可能拦了 |
| `HTTP 401` + `Authentication Fails` | key 错了或没生效 | 重新 `setx` 后**必须重开终端**；检查有没有多余空格引号 |
| `HTTP 402` + `Insufficient Balance` | 余额不足 | 去充值 |
| `HTTP 400` + `Model Not Exist` | 模型名错了 | 用 `deepseek-chat`（通用）或 `deepseek-reasoner`（推理） |
| 一堆乱码 | 中文编码问题 | PowerShell 里加 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` |
| 卡住不动 | 网络慢 | 加超时：curl 后面加 `--max-time 30` |

### 第 2 层 · 上手层（⏱ 20-25h ｜ 📅 **学完 SpringBoot 后，和苍穹外卖并行**）

**目标**：用 **Java + Spring AI** 写出第一个能跑的工具调用。

| 学什么 | 资源 |
|---|---|
| **Spring AI 1.0**（2025-05 已 GA） | [Spring AI 官方文档](https://docs.spring.io/spring-ai/reference/)｜[java-ai-in-action/framework-compare](https://github.com/java-ai-in-action/framework-compare)（Spring AI vs LangChain4j 对比仓库） |
| 结构化输出（JSON Schema） | Spring AI `ChatClient` + `.entity()` |
| **Function Calling** | Spring AI `@Tool` 注解 —— 把你的 `OrderService` 方法暴露给模型 |
| 流式输出（SSE） | Spring AI `Flux<String>` |
| 会话持久化 | 存 MySQL / Redis（**你已有的技能直接用**） |
| Python 最小可用（可选，3-5h） | 函数 / 类 / 装饰器 / async / venv —— **不系统学，够读 LangChain 代码即可** |

**🎯 产出（挂在苍穹外卖上）**：
> 给苍穹外卖加一个**智能客服**：用户用自然语言问"今天有多少订单""哪个菜卖得最好"，模型**调用你写的 Service 方法**拿到真实数据再回答。

**📅 具体做法**：苍穹外卖做到订单模块时，顺手加一个 `AiController`，用 `@Tool` 暴露 2-3 个查询方法。**不要新开项目**——挂在已有项目上，简历上就是"业务系统 + AI 能力"，含金量高于一个孤立 demo。

#### ⭐ 专项评估：智能客服这个模块，到底适不适合现在的你？

> 用户明确问过"我不知道这是什么、会用到什么知识、适不适合现在的我"。下面逐条回答。

**① 它具体会用到什么知识？**

| 环节 | 需要的知识 | 你现在有吗 |
|---|---|---|
| 加一个依赖 | Maven `pom.xml` | ❌ 学 SpringBoot 时会接触 |
| 配置模型 key 和地址 | `application.yml` | ❌ SpringBoot 第 2 步会学 |
| 写一个 REST 接口 | `@RestController` / `@GetMapping` | ✅ **已学（SpringMVC）** |
| 写查询逻辑 | MyBatis-Plus `selectList` / `selectCount` | ❌ 第 1 步会学 |
| **把方法暴露给模型** | 一个 `@Tool` 注解 | 🆕 **新知识，但只有这一个** |
| 调用模型 | Spring AI `ChatClient` | 🆕 **新知识（API 调用，几行代码）** |
| 限制模型能查什么 | 权限白名单、参数校验 | ✅ **已学（拦截器/参数校验）** |

**结论：7 个环节里，5 个要么你已经会、要么第 1-2 步就会。真正的新知识只有 2 个（`@Tool` 注解 + `ChatClient` 调模型），加起来不到一天。**

**② 它适配你到时候的水平吗？**

**适配，但有个前提条件**：必须等你**做完苍穹外卖的订单模块**再动手。原因：
- 这个模块要暴露"查订单"的能力，**你得先有订单才算得出来**
- 提前做会变成"对着空气写 demo"，学不到东西

**反过来说**：一旦订单模块跑通，这就是**你当时能力范围内最"顺手"的 agent 练习**——因为你不需要学新业务，只需要给已经写好的 Service 加一个注解。

**③ 技术难度是高了还是低了？**

**偏低——这既是优点也是缺点，要如实告诉你。**

**优点**：入门门槛低，不会卡住你。
**缺点**：严格说它只是 **Function Calling（单轮工具调用）**，不是真正的 Agent。

| 形态 | 一句话特征 | 你的智能客服是哪种 |
|---|---|---|
| 普通对话 | 模型自己编 | ❌ |
| **Function Calling** | 模型调一次工具、拿结果、回答，**结束** | ✅ **就是这种** |
| Agent | 模型**自己循环**：想→调→看→再想→直到完成 | ❌ 不是 |

**所以面试时不能说"我做了个 Agent"**，说了会被追问穿。正确说法是：
> "我做了 **Function Calling** 的落地，并且评估后**故意没上 agent** —— 因为单轮查询已经满足需求，上 agent 会引入不确定性、更难调试，还更贵。"

**这句话的含金量比"我做了个多智能体系统"高得多**，因为它证明你有设计判断力，而不是堆技术。（这也是 Anthropic 那篇文章的核心观点，正好呼应第 1 层步骤 1。）

**④ 性价比高吗？**

**非常高。** 投入产出账：

| 项目 | 数值 |
|---|---|
| 新增学习成本 | 约 **15-20 小时**（`@Tool` + `ChatClient` + 调试） |
| 开发期间 API 花费 | **1-2 元**（这个模块调用量极小：每次问答约 500-2000 token） |
| 简历收益 | 苍穹外卖从"跟教程的 CRUD 项目"变成"业务系统 + AI 能力" |

**⑤ 有什么风险？**（这部分必须说，否则是骗你）

| 风险 | 严重程度 | 怎么防 |
|---|---|---|
| 🔴 **权限越界**：模型能调用你暴露**任何**方法，如果暴露了 `deleteOrder` 就危险了 | 高 | **只暴露只读查询方法**，方法名带 `query`/`get` 前缀；绝不暴露写操作 |
| 🔴 **SQL 注入 / 参数污染**：模型生成的参数不可信 | 高 | `@Tool` 方法内部必须做参数校验，绝不拼接 SQL |
| 🟡 **烧钱**：用户狂刷导致 token 爆掉 | 中 | 加限流（**你秒杀项目学过令牌桶，直接迁移**）+ 控制台设消费限额 |
| 🟡 **答错误导**：模型把查到的数据解释错 | 中 | 让它"只根据查询结果回答"，并在返回里带上原始数据 |
| 🟡 **业务数据泄露**：用户问到别人的订单 | 中 | 从登录态（JWT）取用户 ID，**不接受模型传用户 ID** |
| ⚪ **维护负担**：模型升级/接口变动 | 低 | Spring AI 已 GA，接口相对稳定 |

**⑥ 有没有更适合当"第一个 agent 练习"的场景？**

有，而且更简单——**先做一个 20 分钟的最小版本热身**：

> 在苍穹外卖项目里写一个 `@Tool` 方法 `queryTodayOrderCount()`，返回一个数字，然后让模型回答"今天有多少单"。**就这一个方法，不接数据库都行**（先返回假数据跑通链路）。

**为什么建议先做这个热身**：
- 20 分钟就能看到"模型调用我的代码"这件事真实发生
- 没有任何风险（不接数据库、不暴露业务）
- **心理收益大**：你会立刻明白"原来就这么回事"

跑通之后再扩展成完整的智能客服。

**⑦ 最终结论**

> ✅ **适合，但排在苍穹外卖的订单模块之后，而且要先做一个 20 分钟的最小热身。**
> ⚠️ **定位要摆正**：它是 **Function Calling 练习，不是 Agent**。简历和面试都按这个说，别夸大。
> 🔴 **三条硬约束**：只暴露只读方法、方法内必须校验参数、必须加限流和消费限额。
>
> **它对你的真正价值不是"学会了 agent 技术"，而是"亲手验证了模型调用我的后端代码"这件事**——一旦验证过，后面 RAG 和 Agent Loop 就都是同一套思路的延伸。

**目标**：搞懂检索增强全流程，这是**面试必问**的重头。

**🎯 产出（挂在黑马点评上）**：
> 给黑马点评加一个**商户知识库问答**：把商户详情/评价灌进 pgvector，用户提问走 RAG 检索 + Redis 语义缓存。

> **面试话术**："我用 Redis 做了语义缓存，把相似 query 的命中率提到 X%，同时用后端限流保护 Embedding 接口。"

**⚠️ 这层的价值**：RAG 是**后端工程师最容易做出差异化**的地方——它本质是"检索 + 缓存 + 排序"，全是你的主场。

| 学什么 | 说明 |
|---|---|
| **手写 ReAct Agent Loop** ★ | **不用框架**手写思考-行动-观察循环，理解终止条件。然后可用 LangGraph 重写一遍对比 |

## 四、关键认知：什么会过时，什么不会

> 这层判断力比多学一个框架重要得多。

| 一年就可能过时 | **底层不会变** |
|---|---|
| 具体框架 API（LangChain 版本、CrewAI） | **RAG 检索工程**（分块/混合检索/重排/评测） |
| 模型名与价格 | **上下文与记忆管理** |
| Agent 产品（各种 CLI/IDE 助手） | **工具调用与协议抽象**（Function Call → MCP） |
| 具体 Prompt 技巧 | **可靠性工程**（重试/幂等/状态持久化/限流/降级/可观测） |
| 向量库 API | **成本-延迟-质量三角** |
| — | **并发 / 缓存 / MQ / 数据库基础** ← 你正在学的 |

**自检问题**（判断一个知识点值不值得深挖）：
> 这个知识点是在描述**"当前模型能力不足的权宜之计"**，还是在描述**"信息如何被检索、约束、验证、编排"**？
> 前者会过期，后者不会。

**行业现实提醒**：KPMG 2025 报告——67% 的组织在试验 agent，**仅 11% 上了生产**；Gartner 预测 2027 年底前 40%+ 的 agentic 项目会被取消。**所以"能落地"的人比"会玩框架"的人值钱得多——这恰好是你的后端背景优势。**

## 六、常见坑（新手必看）

1. 🔴 **一上来啃 LangChain 源码 / 追框架** → 先裸调 HTTP API + 手写循环，理解本质再上框架
2. 🔴 **跳过手写 ReAct 直接用 LangGraph** → 不理解循环和终止条件，调不动、答不出
3. 🔴 **盲目多智能体** → Anthropic 明确建议：**workflow 能解决就别上 agent**。面试说"我评估后没用多智能体，因为单 agent 够用"比堆技术点加分
4. 🔴 **只做 demo 不碰工程** → 重试/限流/超时/成本/权限/评测一个不碰，面试一问就露。**这是你最容易避免的坑（后端背景）**
5. 🟡 **Python 系统学一遍** → 不必！函数/类/装饰器/async/venv 够读代码就行
6. 🟡 **忽视 MCP** → 2026 已成标准，JD 直接写，学几天就能写一个 Server
7. 🟡 **忘设消费限额** → agent 死循环能一夜烧掉几百块
